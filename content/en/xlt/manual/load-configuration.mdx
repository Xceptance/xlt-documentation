Before executing a performance test, define the load profile applied to the application. Configure load settings in `<testsuite>/config/test.properties` (or an alternative profile specified via `com.xceptance.xlt.testPropertiesFile`).

XLT load configurations govern three primary dimensions:
1. **[Load Models](#load-models)**: How load is generated (concurrent user count vs. target transaction arrival rate).
2. **[Load Factor](#load-factor)**: A global or per-scenario scaling multiplier.
3. **[Load Profiles](#load-profiles)**: How load scales over time (static, ramp-up, or variable curves).

## Load Models

A load model determines whether XLT controls concurrent user concurrency or transaction throughput.

### User Count Model (Concurrency-Based)

The **user count model** applies static concurrency. You define the exact number of concurrent users running scenarios in a loop:

* **Behavior**: If configured for 50 users, XLT executes 50 concurrent threads. As soon as a user finishes an iteration, it immediately begins the next (after any configured think time).
* **Throughput Dependency**: Total completed transactions per hour fluctuate with application response times. Faster responses yield higher throughput; slower responses reduce throughput.
* **Best Used For**: Baseline single-user benchmarks, capacity stress tests under fixed concurrency, and repeatable performance regression tests.

<a id="arrival-rate-model"></a>
### Arrival Rate Model (Throughput-Based)

The **arrival rate model** applies dynamic, closed-loop concurrency to achieve a specified hourly transaction rate:

* **Behavior**: If configured for 3,600 transactions/hour, XLT initiates one transaction every second, regardless of current response times.
* **Elastic Concurrency**: When response times are fast, XLT requires fewer concurrent users to meet the arrival rate. If the application slows down, XLT dynamically launches additional virtual users to maintain the target throughput.
* **Feedback Loop & Safety Ceiling**: If an application begins to degrade under load, increasing virtual users can compound server stress. To protect against runaway overload, specify a maximum user ceiling alongside the arrival rate.
* **Best Used For**: Real-world traffic simulation, SLA verification, and peak hourly order volume validation.

:::note[User Count acts as Concurrency Ceiling]
When defining an arrival rate, always set `users` as well. In arrival rate mode, `users` serves as the hard ceiling for concurrent threads to protect the application from unbounded growth.
:::

## Load Factor

The **load factor** scales configured load values without requiring you to recalculate individual user counts or arrival rates:

```properties
## Scale TVisit to 150% and default all other scenarios to 10%
com.xceptance.xlt.loadtests.TVisit.loadFactor = 1.5
com.xceptance.xlt.loadtests.default.loadFactor = 0.1
```

The load factor scales both user counts and arrival rates. XLT rounds calculated values up to the nearest integer. To disable a test case entirely, explicitly set `loadFactor = 0.0`.

## Load Profiles

Load profiles govern how load changes over the duration of the test:

### Static Load Profile

The load remains constant throughout the measurement period:

```properties
com.xceptance.xlt.loadtests.TVisit.users = 500
com.xceptance.xlt.loadtests.default.measurementPeriod = 1h
```

<a id="ramp-up-load-profile"></a>
### Stepped and Ramp-Up Load Profiles

A ramp-up profile gradually increases load to warm up application caches, JIT compilers, and connection pools:

* `rampUpPeriod`: Total duration of the ramp-up phase.
* `rampUpInitialValue`: Starting user count or arrival rate.
* `rampUpSteadyPeriod`: Duration to hold the load at each step (mutually exclusive with `rampUpPeriod`).
* `rampUpStepSize`: Incremental user or arrival rate increase applied at each step.

#### Stepped Ramp-Up Example

```properties
com.xceptance.xlt.loadtests.TVisit.users = 500
com.xceptance.xlt.loadtests.TVisit.rampUpSteadyPeriod = 10m
com.xceptance.xlt.loadtests.TVisit.rampUpStepSize = 100
com.xceptance.xlt.loadtests.TVisit.rampUpInitialValue = 100
com.xceptance.xlt.loadtests.TVisit.measurementPeriod = 60m
```

![Stepped Ramp-Up Profile](/images/user-manual/chart_rampup.svg)

#### Linear Ramp-Up Example

To configure a smooth linear ramp-up to maximum load, specify `rampUpPeriod`:

```properties
com.xceptance.xlt.loadtests.TVisit.users = 500
com.xceptance.xlt.loadtests.TVisit.rampUpPeriod = 40m
com.xceptance.xlt.loadtests.TVisit.measurementPeriod = 60m
```

### Variable Load Profile

The variable load profile gives you full control to vary the load parameter during the test. You can increase or decrease the load at any time.

This is useful for combining different load levels in one run (e.g., alternating regular and peak loads) or modeling a 24-hour day in a shorter period.

Define the load variation using a load function: a sequence of time/value pairs representing points where the slope changes. XLT connects these points with straight lines.

Separate multiple pairs with spaces, commas, semicolons, or tabs. The time format supports standard [time periods](/xlt/manual/test-suite-configuration/#time_period_values).

:::note
Do not use whitespace within a time unit or between time and value (e.g., `1 h` or `1h / 10`). To avoid ambiguity, we recommend using commas or semicolons to separate time/value pairs.
:::

Example load function:

```properties
com.xceptance.xlt.loadtests.default.loadFactor = 0/10, 60m/10, 60m/20, 70m/5
```

This keeps the load at 10 for one hour, doubles it to 20, decreases it to 5 over ten minutes, and maintains it at 5 for the remainder.

![Variable Load Factor Profile](/images/user-manual/chart_variable_load_factor.svg)
*Figure: Dynamic load curve defined by time/value coordinates.*


Pairs must be sorted by time (ascending). You can specify two pairs for the same time to create an immediate jump. If no pair is defined for time "0", XLT inserts a starting point with the smallest non-zero user/arrival rate (1) or load factor (0.001), creating a ramp-up. If the test runs longer than the last pair, the last value is held constant.

#### Relative Load Functions

You can specify times and values relative to the previous point using `+` or `-`:

```properties
## This load function is equivalent to "0/1.0, 1h/1.5, 1h30m/0.5"
com.xceptance.xlt.loadtests.default.loadFactor = 0/1.0, +1h/+0.5, +30m/-1.0
```

Absolute and relative pairs can be mixed. Relative times cannot result in a negative time (pairs must remain sorted).

```properties
## This load function is equivalent to "0/1.0, 1h/1.0, 1h20m/2.0, 1h40m/2.0, 2h/1.0"
com.xceptance.xlt.loadtests.default.loadFactor = 0/1.0, 1h/+0, +20m/2.0, +20m/+0, +20m/1.0
```

If the first pair is relative, a minimal non-zero start point is assumed at time 0:

```properties
## This load function results in "0/0.001, +1h/+1.0", +1h/+0.5", i.e. "0/0.001, 1h/1.001, 2h/1.501"
com.xceptance.xlt.loadtests.default.loadFactor = +1h/+1.0 +1h/+0.5
```

## Load Test Phases

Execution of a load test scenario occurs in four phases: initial delay, warm-up, measurement, and shutdown.

* **Initial Delay** (`initialDelay`): Optional. Delays the start of a scenario. Useful if the scenario depends on data from another running scenario.
* **Warm-up Period** (`warmUpPeriod`): Optional. Time for the system to reach optimal performance (e.g., populating caches) before measurements begin. Data collected during this period is discarded.
  * _Tip:_ We recommend omitting the warm-up period and instead using a time filter on the test report. This ensures all data is captured and available for analysis if needed.
* **Measurement Period** (`measurementPeriod`): **Required**. The main phase where test data is recorded.
* **Shutdown Period** (`shutdownPeriod`): Optional. Allows users to complete their current iteration or perform cleanup after the measurement period. Users stop when finished or are forcibly terminated when this period ends. Without a shutdown period, users stop immediately after the measurement period.

The **ramp-up period** is often part of the warm-up to ensure stable performance during measurement. However, if you want to analyze behavior during ramp-up, do not define a warm-up period.

:::warning[Ramp-Up is Overwritten by Load Functions]
If a load test scenario defines a function instead of a constant value for users, arrival rate, or load factor, that function alone defines the load curve's shape. Any ramp-up parameters specified for this scenario are ignored in this case, and the ramp-up period will not be displayed in the _Load Profile_ section of the test report created for a run with this setting.
:::

## Virtual Threads and High Concurrency

In XLT, each virtual user is executed in its own thread to maintain a straightforward, synchronous programming model. 

Starting with XLT 10, user activities are executed using Java 21 **virtual threads** by default. Virtual threads are lightweight user-mode threads managed by the JVM runtime rather than directly by the operating system kernel:

* **Platform Threads (Legacy)**: Each user allocates a dedicated OS thread with an operating system stack (typically ~1 MB). Sizing agents for thousands of users requires substantial RAM and frequently runs into operating system thread limits or scheduling overhead.
* **Virtual Threads (Default)**: Virtual threads store call stacks as objects in JVM heap memory. Tens of thousands of virtual threads run cooperatively on a small pool of native carrier platform threads, slashing idle memory footprint and enabling unprecedented concurrency per load generator.

### Enabling or Disabling Virtual Threads

Virtual threads are enabled by default. If your test suite or third-party libraries require standard platform threads, you can disable virtual threads in `project.properties` or `test.properties`:

```properties
## Enable or disable virtual threads (default: true)
com.xceptance.xlt.virtualThreads.enabled = false
```

### Carrier Thread Pool Tuning

Virtual threads are scheduled onto a small pool of native carrier threads (typically defaulting to the number of available CPU cores, up to 256). You can configure the maximum number of carrier threads by setting the following JVM property in `<xlt>/config/jvmargs.cfg`:

```properties
-Djdk.virtualThreadScheduler.maxPoolSize=256
```

For detailed capacity planning and hardware sizing recommendations, see [How to Size Your Test Environment](/xlt/how-tos/test-sizing/). For test suite code migration guidelines, see [Test Suite Configuration](/xlt/manual/test-suite-configuration/#virtual-threads).
