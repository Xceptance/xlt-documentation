The _Configuration_ view of a load test project resembles basic [project configuration](/xtc/basics/project-configuration/), with several settings specific to load testing:

## Repository

:::info[Role Required]
To view repository settings, your account must at least have the role of a [tester](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::
:::info[Role Required]
To edit repository settings, your account must at least have the role of a [test manager](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

In addition to the [basic repository settings](/xtc/basics/project-configuration/#repository) shared between load test and monitoring projects, load test projects include build and compilation options for the test suite.

## Code archives

:::info[Role Required]
To view repository settings, your account must at least have the role of a [tester](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::
:::info[Role Required]
To edit repository settings, your account must at least have the role of a [test manager](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

As an alternative to Git-based source repositories, load testing projects allow uploading source code archives (ZIP files). Under the **Code Archives** tab of the project configuration, you can upload new archives, edit metadata, and delete obsolete archives.

For full details on prerequisites, retention rules, and automated uploads via the REST API, see [Code Archives](/xtc/loadtesting/code-archives/).

## Build

### Build tool

Before a load test starts, XTC compiles your load test suite. If you do not configure a build tool, **Maven** runs by default. XTC also supports **Gradle** as an alternative. Verify that your repository contains the required build files and that the build succeeds locally before running in XTC.

To configure a build tool, click the edit button, select the tool, and enter optional arguments. Click _Save Changes_ to confirm.

![](/images/xtc/loadtest_selectBuildTool.png)

### Build artifact and dependency cache

Building a load test suite before test execution can take several minutes. Most build time is spent compiling sources or downloading dependencies (XLT and third-party libraries).

To reduce startup times, XTC caches two separate parts of the build process:
* **Dependency cache**: caches downloaded project dependencies so later builds skip re-downloading them.
* **Build artifact cache**: caches the compiled load test suite. For new load test runs, XTC restores the project directly from this cache, skipping compilation entirely. This cache remains active as long as the Git commit or code archive does not change. New revisions trigger a fresh build that still benefits from the dependency cache.

Both caches expire and clear automatically 14 days after the most recent load test run.

To reset corrupted or stale caches manually, navigate to this section, and click **Discard Cache**.

## Default sharing settings

:::info[Role Required]
To view default sharing settings, your account must at least have the role of a [tester](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

:::info[Role Required]
To edit default sharing settings, your account must at least have the role of a [test manager](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

In _Sharing_, define the default expiration period for shared [load test results](/xtc/loadtesting/results/#sharing-results) and [load test reports](/xtc/loadtesting/reports/#sharing-a-report). New result and report shares use this default duration automatically, though individual links can use custom expirations. You can deactivate, extend, or reactivate all shares adhering to the default at once.

Using the default expiration ensures that updating the project-wide duration updates existing shares accordingly.

The maximum lifetime of a share is 180 days.

:::note
Default expiration dates for results and reports operate as independent settings.
:::

### Removing all custom share links

:::info[Role Required]
To use this feature, your account must at least have the role of a [test manager](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

You can set custom expiration dates for specific results and reports rather than using the global preset. These custom links remain unaffected when modifying or disabling the [project-wide default expiration date](#default-sharing-settings). To clear custom links, click _Remove Custom Report Shares_ or _Remove Custom Result Shares_ beneath the default sharing controls. Both actions require confirmation and cannot be undone.

## Properties

:::info[Role Required]
To view properties, your account must at least have the role of a [tester](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

:::info[Role Required]
To edit properties, your account must at least have the role of a [test manager](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

In _Properties_, configure global [properties](/xlt/manual/test-suite-configuration/) or [secret properties](/xlt/manual/test-suite-configuration/#secret-properties) for test execution.

[Secret properties](/xlt/manual/test-suite-configuration/#secret-properties) behave like standard properties, but mask their values with ****** in load test reports and downloaded result datasets.
When editing an existing secret property in the UI, its current value displays as \*\*\*. Overwrite \*\*\* to change the value.

Projects can **inherit properties** (both standard and secret) defined at the organization level. Organization-level changes apply immediately to the project. Projects can define project-specific properties that override inherited properties sharing the same key.

Properties configured at the project level apply to all new load tests, while [properties set on a specific load test](/xtc/loadtesting/lt-settings/) apply only to that test. Test-level properties override project-level definitions. Properties not declared in XTC are loaded directly from project configuration files.

## Environment

Load tests execute using XLT, Xceptance's load and performance testing engine. XLT develops independently from XTC. Periodic major releases introduce new capabilities, which can occasionally alter compatibility.

When a major XLT version is released, XTC supports both the previous and new execution environments during a transition window.

XLT follows a clear deprecation policy: when a new major version becomes available, **the previous major version** is marked deprecated, but **remains available for 8 weeks**. This window allows you to run existing load testing workflows uninterrupted while scheduling suite migrations. **After the 8-week migration period, XTC retires the older version** and standardizes on the new release.

Project administrators choose the default XLT version in project settings under _Project > Configuration > Execution > Execution Environment_. Update this setting when starting a new project or after completing test suite migration. The chosen default applies to new load tests, but does not alter duplicated tests.

Testers can override this default for an individual load test under _Load Test > Settings > Common Machine Configuration_. This enables verifying migrated code branches on the new environment before promoting the version project-wide.

:::note[What about minor version changes?]
Minor updates (such as 6.0.1 or 6.1.0) maintain backward compatibility and require no migration. XTC applies minor updates automatically, and release notes record version changes.
:::
