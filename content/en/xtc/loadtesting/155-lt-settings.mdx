## Test settings

The _Settings_ tab contains configuration options for the test run. Complete all mandatory fields before starting the test.

:::note
You cannot edit test settings once execution starts.
:::

:::info[Role Required]
To edit test settings, your account must at least have the role of a [tester](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

:::info[Role Required]
To view test settings, your account must at least have the role of a [reviewer](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

### Load profile

Under _Load Profile_, you can override test suite settings for the [test properties file](/xlt/manual/test-suite-configuration/#test-properties-file). You can also override test duration, ramp-up time, shutdown time, and [load factor](/xlt/manual/load-configuration/#load-factor).

Load profile overrides let you adjust parameters quickly—such as extending duration or testing higher load factors—without pushing changes to the repository or editing property files. If left blank, XTC applies the settings declared in the test suite.

When overriding load profile settings, specify values for each parameter, including ramp-up and shutdown times. Load factor formulas require a ramp-up time of zero. The preview graph displays the resulting load curve:

![Overwriting the Load Profile with a Load Function](/images/xtc/load_profile_overwrite.png)
*Overwriting the Load Profile with a Load Function*

Read more in the _Load Testing_ guide about [configuring load profiles](/xlt/manual/load-configuration/).

:::tip[Load Factor and Machine Scaling]
When using a **Load Factor** greater than 1.0 (such as `2.0` to simulate double the baseline load), concurrency on each agent increases proportionally. Ensure your machine configuration allocates sufficient agent instances to handle the scaled concurrency, or adjust your instance count on the **Machines** tab.
:::

### Properties

In _Properties_ and _Secret Properties_, you can override [properties](/xlt/manual/test-suite-configuration/) for test execution. Values set here take precedence over project-level and organization-level settings.

Load tests can inherit project-level properties. You can also define test-specific properties that override matching project-level keys. Properties not defined in XTC load directly from the test project files.

### Repository

Under _Repository_, specify a repository branch for this test run. This override is useful when testing branches that differ from the [project default branch](/xtc/basics/project-configuration/#repository). If left blank, XTC checks out the default branch configured for the project.

### Code archive

Under _Code Archive_, configure the load test to run using an uploaded ZIP archive instead of Git. Select a specific version of your uploaded archives or choose **Use Latest** to run with the most recently uploaded archive.

You must explicitly enable code archives for the load test. For details on managing and uploading archives, see [Code Archives](/xtc/loadtesting/code-archives/).

## Machine configuration

Configuring test machines is mandatory. Access machine settings on the _**Machines**_ tab.

Select test machines from public cloud providers (Amazon, Google Cloud, or Hetzner), custom machines, or your own [private machines](/xtc/loadtesting/private-machines/). You can also combine these machine types within a single test.

When using public cloud machines, enter your machine requirements. XTC provisions and starts the selected instances before the test and terminates them afterward. To configure cloud machines, click the edit button next to the section heading:

* specify target _regions_ (XTC distributes instances across selected regions as evenly as possible),
* select an _instance template_ based on required computing power,
* enter the number of machine instances to launch (_instance count_), and
* specify the number of _agents per instance_.

Because [test sizing](/xlt/how-tos/test-sizing/) depends on test design, monitor CPU and memory usage after the test run to tune machine sizing for future executions.

### Private machines

If private machines are enabled for your organization, request the required count of private machines by capacity class in the **Private Machines** section on the **Machines** tab.

When the load test begins, XTC locates available private machines of the requested type and reserves them for the test duration. If insufficient machines are registered and online, the test fails to start.

For guidance on registering and maintaining your own infrastructure, see [Private Machines](/xtc/loadtesting/private-machines/).

In _**Common Machine Configuration**_, set a communication password for traffic between master and agent machines (XTC generates a random password by default). You can also [override the default XLT execution environment version](/xtc/loadtesting/load-project-configuration/#environment) here.

## Notifications

XTC can send notifications when a load test changes state.

Supported notification channels include:

* **Slack**: configure the [Slack integration](/xtc/integrations/slack/) for your project. XTC delivers updates on [load test state changes](/xtc/integrations/slack/#load-tests) directly to the specified Slack channel.
* **Email**: open the _Notifications_ section of the _Settings_ tab and add recipient email addresses. XTC notifies these addresses when the load test finishes. To disable notifications, clear the address list.
