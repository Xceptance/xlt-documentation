XTC organizes all tests into test projects, which in turn belong to an organization.

Only an XTC administrator can create organizations. The administrator assigns an initial organization administrator who can invite members and create projects.

## Organization configuration

:::info[Role Required]
To use this feature, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

On the **General** tab of the _Configuration_ page, edit the organization name, short name, and description. You can also upload an organization logo for the dashboard list.

On the **Repository** tab, configure default Git repository settings (including repository URL, HTTPS credentials, or SSH key authentication) that child projects can inherit.

On the **Properties** tab, define regular and secret properties at the organization level. Projects within the organization can inherit these properties to prevent duplicate setups.

On the **Security** tab, turn [user invitations](#inviting-users-to-join-xtc) on or off and set [authorization requirements](#mandatory-login-requirements) for organization members.

On the **Integrations** tab, connect XTC with a Slack workspace to receive event notifications such as load test status changes. For details, see the [Slack integration](/xtc/integrations/slack/).

## User roles within an organization

An organization member holds one of four roles:

* **Guest**: views only the organization dashboard.
* **Member**: views organization settings and accesses assigned projects. This is the default role for new users.
* **Billing manager**: views and evaluates organization [resource usage](/xtc/loadtesting/resource-usage/).
* **Organization administrator**: manages all organization projects, members, and configuration settings.

Permissions increase hierarchically. For example, a billing manager retains all member permissions plus billing access.

When viewing an organization, your current role appears in the footer on the bottom right:

## Adding members to an organization

:::info[Role Required]
To use this feature, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

To add members, select _Members_ in the left menu. The page displays existing members, their [authentication settings](#mandatory-login-requirements), and their last login timestamp.

Click `+` in the top right to add a member. Enter the account email address and select an organization role. The user must already hold an active XTC account.

To add users in bulk, paste a list of email addresses separated by commas, newlines, or spaces. All listed users receive the chosen role.

:::note
The _Members_ page displays the [login provider](/xtc/basics/user-accounts/#connecting-existing-xtc-accounts-to-an-external-login-provider) for each member and indicates whether they enabled [2FA](/xtc/basics/user-accounts/#two-factor-authentication). Administrators can quickly verify compliance with organizational security policies.
:::

Explicitly assigning organization members is rarely required during routine operations, as [adding project members](/xtc/basics/projects/#adding-and-removing-project-members) grants organization membership automatically.

### Inviting users to join XTC

:::info[Role Required]
To use this feature, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

Organization administrators can invite users without an existing account when user invitations are [enabled](#organization-configuration). Follow the steps to [add users to the organization](#adding-members-to-an-organization), and activate the _Invite Users_ toggle.

Invited users receive an email with a registration link to choose a password and complete their profile.

Invitations expire after 30 days. Administrators can resend pending invitations from the _Members_ page. Unclaimed invitations are automatically removed after 90 days.

## Editing and removing organization members

:::info[Role Required]
To use this feature, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

To **update a user role**, navigate to _Members_, open the context menu next to the user name, and select _Edit Role_.

To **remove a member**, open the context menu next to the user name, select _Remove_, and confirm the prompt.

## User groups

:::info[Role Required]
To create, update and delete user groups, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

Managing large organizations with many projects and users requires streamlined access controls. User groups simplify this process by grouping organization members under a shared identity.

Like individual members, you can assign user groups to a project with a specific role. All members within the group become indirect project members with identical permissions.

For example, you can create groups named "Admins", "Test Managers", "Testers", and "Reviewers":
1. Open the _Members_ page and select the _User Groups_ tab.
2. Click **New** to create a user group.
3. Select _Add Org Members to Group_ to populate the group with existing members.
4. Open the group details to add or remove individual members.

Next, assign these groups to your projects. Navigate to the project _Members_ page, switch to the _User Groups_ tab, and add each group with the appropriate project role.

When adding a new user, simply assign them to the relevant user group. The user immediately receives the corresponding role across all projects associated with that group.

You can combine direct project members and user groups to accommodate custom requirements.

### Effective role

When users belong to projects both directly and through groups:

* Direct membership takes precedence. Direct members receive the role assigned to their account.
* Indirect members receive the highest role among their assigned user groups.

### Known limitations

Indirect project members cannot use the following features:

* Remembering last visited projects.
* Starring projects for quick access.

## Locking members of an organization

:::info[Role Required]
To use this feature, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

If a user fails to meet organizational security requirements, lock their account either [automatically](#mandatory-login-requirements) or manually. Locked users remain in the organization directory, but cannot view data or perform actions.

To lock a user manually, navigate to _Members_, locate the account, and select _Lock Member_ from the context menu. To restore access, select _Unlock Member_.

## Mandatory login requirements

:::info[Role Required]
To use this feature, your account must have the role of an [organization administrator](/xtc/basics/projects/#user-roles-within-a-project) within the project.
:::

Organization administrators can enforce specific authentication requirements on members, such as approved [login providers](/xtc/basics/user-accounts/#connecting-existing-xtc-accounts-to-an-external-login-provider) or [2FA](/xtc/basics/user-accounts/#two-factor-authentication).

:::note
This configuration restricts organization access rather than general XTC login. Users can still log into XTC and view the organization on the dashboard, but cannot open organization projects until they meet the required login method.
:::

When accessing an organization, XTC verifies that the current active session meets all login criteria. Users configured with both an external provider and 2FA must use the specific authentication flow mandated by that organization.

:::warning
Login policy updates take effect immediately. Signed-in users see a lock-out screen upon their next request if they do not meet the new policy. Schedule policy updates outside core operating hours to reduce disruption.
:::

:::note
XTC does not currently enforce both 2FA and single sign-on (SSO) simultaneously. To require both, configure your external SSO provider as the sole allowed login method and mandate 2FA within that identity provider.
:::

### Mandatory two-factor authentication

To mandate 2FA, open the organization _Configuration_, select the _Security_ tab, and edit _Access Requirements_. Choose _Two-Factor login required_ and save your changes.

:::warning[Accidental Lockout]
If you are not currently signed in using 2FA, XTC warns you about locking yourself out of the organization. Heed this warning carefully. Saving this configuration prevents you from accessing the organization or modifying login requirements if you lack 2FA credentials.
:::

### Mandatory login through an external provider

To mandate external authentication, navigate to organization _Configuration_, open the _Security_ tab, and edit _Access Requirements_. Select _SSO login required_ and save your changes.

![Mandatory External Login Provider with a specific issuer URL.](/images/xtc/login_requirement_sso.png)
*Mandatory External Login Provider with a specific issuer URL.*

Administrators can restrict access to specific identity providers by entering their issuer URLs into the text field. Issuer URLs match the `iss` claim in the OpenID Connect token issued by your provider (such as `https://accounts.google.com`). Enter each URL on a separate line to permit more providers.

:::warning[Accidental Lockout]
If you are not currently signed in through an external provider, XTC warns you about locking yourself out of the organization. Heed this warning carefully. Saving this configuration prevents you from accessing the organization or modifying login requirements if you are not signed in through an approved provider.

Administrators should sign in through the intended identity provider before enforcing this policy. XTC validates your current issuer against the entered list to highlight typos immediately.
:::
