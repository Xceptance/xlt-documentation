:::

## General

The _Configuration_ section of a monitoring project closely resembles basic [project configuration](/xtc/basics/project-configuration/), with a few settings specific to monitoring projects. The following read-only settings are displayed for informational purposes and can only be modified by XTC administrators:

* _Data Persistence_ (how long data like execution history persists in storage), and
* _Execution Environment_ (IP addresses of agent machines running monitoring scenarios).

## Dynamic repository branch

In the repository configuration, you can specify a static branch name or define a resource URL. From this URL, XTC extracts the branch name dynamically using a regular expression. This approach helps tie scenario execution directly to the application version currently deployed.

## Scenario defaults

On the _Scenario Defaults_ tab in _Configuration_, you can define [default settings](/xtc/monitoring/scenarios/#scenario-settings) for all monitoring scenarios, including the default Reply-To address and alert notification toggles. You can override these defaults for each individual scenario. To edit scenario defaults, click the edit button on the right of any section:

## Notification lists

XTC provides fine-grained control over when alerts trigger and who receives them. Instead of relying on a single recipient list, you define dedicated **notification lists** and link them to specific trigger conditions using [**quality sensors**](#quality-sensors).

Notification lists are configured on the _Notifications_ tab of the project configuration.

In a typical project, notification lists map to operational responsibilities:

* **On-Call Team**: evaluates scenario failures and initiates operational responses.
* **Monitoring Dev Team**: maintains scenario scripts and resolves test failures.
* **App Dev Team**: investigates application performance issues and regressions.

Configure the default **Reply-To Address** for notification emails on the **Scenario Defaults** tab. If left blank, this defaults to a no-reply address. Set a dedicated team inbox to receive replies.

### Defining a notification list

To add a notification list, navigate to the _Notifications_ tab in _Configuration_ and click _New_. Enter a name and optional description for the list.

The new notification list appears in the overview table.

![Notification lists overview table.](/images/xtc/monitoring_notificationLists_overview.png)
*Notification lists overview table.*

Use the context menu to edit the name and description, duplicate the list, or delete it after confirmation. You can also [pause or disable](#pausing-or-disabling-notifications) notifications for a single list.

To view subscribers and verify assignments, click the list name or select **View** from the context menu.

![Notification list detail view.](/images/xtc/monitoring_notificationLists_details.png)
*Notification list detail view.*

To add subscribers, open the _Subscribers_ tab in the list detail view and click _Add_. You can add **XTC user subscribers** (existing accounts with stored contact data) or **custom subscribers** (custom email address, phone number, or push topic). Supported channels include email, **push notifications** (via [ntfy.sh](https://ntfy.sh)), and [**Slack channels**](/xtc/integrations/slack/). You can update subscriber details at any time, or deactivate and remove subscribers.

#### Push notifications setup

To receive instant monitoring alerts on a mobile device:

1. Install the **ntfy** app on your mobile device (available for iOS and Android).
2. Open your account settings and navigate to **Profile > Push Notifications**.
3. Generate a unique notification topic and scan the QR code with your mobile device. The ntfy app subscribes to your topic automatically.
4. Click **Send Test Message** in XTC to verify that notifications arrive.
5. In your project's **Notification List**, edit a user or custom subscriber and enable the **Push Notification** channel.

:::warning[Deprecation Warning: SMS Notification Channel]
Push notifications replace SMS alerts. The SMS notification channel retires in September 2026. Migrate your notification lists to push notifications as soon as possible.
:::

### Notification list assignments

After configuring a notification list, [assign it to quality sensors](#managing-notification-lists-of-a-quality-sensor). The _Assignments_ tab in the list details page displays every quality sensor referencing the list. Review this tab before modifying a list to see which scenario alerts change.

### Activation times

By default, monitoring alerts dispatch around the clock on every calendar day. While appropriate for critical functional outages, you can restrict minor alerts to business hours.

Activation times define recurring time windows during which notifications reach subscribers. For instance, notifications can run Monday through Friday from 9 AM to 5 PM. You can add up to 20 activation times per notification list. Outside these windows, XTC suppresses notifications.

A newly created activation list is active around the clock by default.

To restrict active hours, open the notification list, and select the _Activation Times_ tab. Edit the default entry or create new time windows with the following properties:

* Name and description.
* Active weekdays.
* Start time.
* End time (including 59 seconds, such that 23:59 extends to 23:59:59).
* Target time zone for the schedule.

You can configure several activation times for different days. Overlapping time windows function normally. Notifications dispatch whenever at least one window is active.

:::note[Warning for Inactive Notification Lists]
Removing all activation times from a notification list leaves it inactive with no alerts sent. XTC displays a warning banner when a notification list lacks active time windows.
:::

### Pausing or disabling notifications

On the project configuration _Notifications_ tab, you can enable or disable notifications globally for the entire project.

To pause notifications and optionally suspend scenario runs for a scheduled window, configure [quiet periods](/xtc/monitoring/quiet-periods/).

To toggle alerts for an individual list, use the list context menu in the notification lists table. An icon in the table indicates the current notification state.

## Quality sensors

A **quality sensor** defines when XTC triggers an alert and [which notification lists](#notification-lists) receive it. Because these criteria apply across scenarios, you configure sensors at the project level and assign them to test scenarios as needed. You can configure multiple quality sensors in a project, and assign several sensors to a single scenario.

### Defining a quality sensor

To add a quality sensor, navigate to the _Quality Sensors_ tab in _Configuration_ and click _New_. Specify a name, description, and failure threshold based on consecutive executions (for example: 1/1 alerts on every failure; 3/3 alerts when a scenario fails 3 consecutive times; 3/10 alerts when 3 of the last 10 executions fail).

![Adding a new quality sensor to the project.](/images/xtc/monitoring_qualitySensors_add.png)
*Adding a new quality sensor to the project.*

![Quality sensors overview.](/images/xtc/monitoring_qualitySensors_overview.png)
*Quality sensors overview.*

The quality sensor appears in the overview table. Use the context menu to edit settings, duplicate the sensor, or delete it after confirmation. To configure metrics and notification lists, click the sensor name or select **View** from the context menu.

![Quality sensor detail view.](/images/xtc/monitoring_qualitySensors_details.png)
*Quality sensor detail view.*

#### Adding metrics to a quality sensor

On the _Configuration_ tab of the quality sensor detail view, define **metrics**: conditions that must all pass for the scenario run to succeed.

To add metrics, open the _Configuration_ tab and click **Add** in the _Metrics_ section. Select criteria from the following categories:

* **General**: checks for execution errors and scenario failures.
* **Event**: checks timing for [page load events](/xlt/manual/client-performance/#metrics-for-perceived-performance) (_DomContentLoaded_, _First Contentful Paint_, _First Paint_, _Load Event_).
* **Web Vitals**: checks [Core Web Vitals criteria](https://web.dev/articles/vitals) (_Cumulative Layout Shift_, _First Contentful Paint_, _First Input Delay_, _Interaction to Next Paint_, _Largest Contentful Paint_, _Time to First Byte_).
* **XLT**: checks runtime limits for transactions, actions, or requests, as well as request errors.

Depending on the metric, configure the threshold as an occurrence check, a duration in milliseconds, or a specific metric parameter. You can edit or delete defined metrics using their context menu.

When a scenario violates a metric threshold across the configured consecutive runs, XTC triggers an alert and notifies the assigned [notification lists](#notification-lists).

#### Managing notification lists of a quality sensor

The [notification lists](#notification-lists) assigned to a quality sensor define who receives an alert when the sensor fails.

To assign a [configured notification list](#defining-a-notification-list) to the quality sensor, open the _Configuration_ tab and click **Add** in the _Notification Lists_ section. Select the target notification list from the dialog.

To detach a notification list, click **Remove** in its context menu on the _Configuration_ tab. This stops alerts for this sensor without deleting the underlying list. To delete a list entirely, [manage it on the project _Notifications_ tab](#defining-a-notification-list).

### Quality sensor assignments

After configuring quality sensors, [assign them to your scenarios](/xtc/monitoring/scenarios/#quality-sensors). The _Assignments_ tab in the sensor details page displays every scenario using the sensor. Check this tab before updating a sensor to verify which scenario runs change.

In a typical project, quality sensors follow a three-tier structure:

* **Preparation**: verifies that the scenario environment is ready and notifies the Monitoring Dev Team list on fatal errors. Blocks execution of later sensors on failure (such as Git download errors or compile issues).
* **Stability**: verifies that the scenario runs without [scenario errors](/xtc/monitoring/history/#execution-statuses). Notifies the On-Call Team and Monitoring Dev Team lists, and blocks execution of later sensors on failure.
* **Performance**: verifies that response times and Web Vitals stay within specified limits. Notifies the App Dev Team when metrics exceed thresholds.

Assign these quality sensors to each scenario in this sequence.

If a scenario requires unique alert thresholds, define a dedicated quality sensor or notification list.
